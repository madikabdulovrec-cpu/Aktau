# Задание: бот «Пульс продаж» M&M Fabrica

> Точка входа для новой Claude-сессии. Задача — построить Telegram-бота, который
> каждые 3 часа присылает в рабочий чат отдела продаж сводку «как идут продажи».
> **Прочитать первым.** Дата подготовки: 2026-05-22.

## 1. Что это и зачем

Бот «Пульс продаж» — Cloudflare Worker с cron-триггером. Каждые 3 часа
(08:00 / 11:00 / 14:00 / 17:00 / 20:00 по Алматы) присылает в рабочий ТГ-чат
отдела продаж короткую сводку: сколько заявок, скорость первого ответа, что
висит без ответа прямо сейчас, и 1–2 конкретных действия.

Зачем. Аудит (`docs/sales/audit.html`): до консультации доходит лишь ~7% живых
заявок — их теряют в середине воронки (медленный ответ, брошенные диалоги).
Сейчас руководитель видит только вечерний отчёт продажника — по памяти, постфактум.
Бот делает потерю **видимой в моменте**, пока заявку ещё можно спасти.

Вечерний отчёт продажника остаётся — бот его не заменяет, а добавляет
объективную картину по цифрам. Чат — тот же, где продажник пишет вечерний отчёт
(решение владельца): команда видит живой статус и сама подхватывает зависшие
заявки.

## 3. Что строим — итог

Один Cloudflare Worker `mm-pulse-bot` с двумя точками входа:
- `scheduled` (cron) — раз в 3 часа считает метрики дня и шлёт отчёт в Telegram;
- `fetch` — приём вебхука message.help (накопление событий дня, если выбрана
  ветка B — см. раздел 4), ручной триггер дайджеста по `?secret=`, healthcheck.

Плюс конфиг `wrangler-mm-pulse-bot.toml` и KV namespace `mm-pulse-kv`.

## 4. Архитектура — сначала разрешить развилку источника данных

Боту нужны данные дня из CRM message.help: новые заявки (живые обращения), время
первого ответа, диалоги без ответа сейчас. Как их получить — зависит от
возможностей API message.help. **Первый шаг новой сессии — изучить API**
(использовать код авторизации из `mh-bot.js`), затем выбрать ветку:

**Ветка A — pull (предпочтительно).** Если API message.help умеет отдавать
список диалогов/сообщений, обновлённых за период («list dialogs», «messages since
timestamp»), — digest-воркер в момент cron сам тянет данные дня. Коллектор и
накопление в KV не нужны. Самый простой вариант.

**Ветка B — webhook-коллектор (если pull-API нет).** Воркер подписан на вебхук
message.help `channel.message`; на каждое событие дописывает его в KV-бакет
текущего дня. В момент cron digest читает бакет и реконструирует день из потока
сообщений.
- **B1** — своя регистрация вебхука для `mm-pulse-bot`, если message.help
  разрешает несколько вебхуков на проект/канал. Чисто, без зависимости от mh-bot.
- **B2** — если разрешён только один вебхук: единый вебхук идёт на `mh-bot`
  (ему сообщения нужны, чтобы отвечать), а `mh-bot.js` дописывает копию каждого
  события в `mm-pulse-kv` (несколько строк — «tee»). Тогда `mm-pulse-bot` — это
  только cron + digest. Минус: зависит от деплоя mh-bot.

Выбранную ветку зафиксировать комментарием в начале `mm-pulse-bot.js`.
Целиться в A; если API не даёт нужного — B1; если один вебхук — B2.

Схема одного события в KV (ветка B):
```
{ dialog_id, contact_id, contact_name, direction: "client"|"operator"|"bot",
  operator_id, ts, is_first_client_msg }
```
Ключ бакета — `events:YYYY-MM-DD` (дата по Алматы). TTL ключа ~48 ч — чистится сам.

**Метрики считает код, не LLM:**
- новых заявок сегодня — число уникальных `dialog_id`, где сегодня появилось
  первое сообщение клиента (живые обращения; служебные и эхо отсекать);
- скорость первого ответа — медиана разницы «первое сообщение клиента → первый
  ответ оператора/бота» по новым диалогам;
- без ответа сейчас — диалоги, где последнее сообщение от клиента и с него прошло
  больше порога (`UNANSWERED_THRESHOLD_MIN`, по умолчанию 20 мин);
- дельта за последние 3 часа — то же в окне [сейчас−3ч; сейчас].

**LLM (Claude API, персона РОП) числа НЕ считает.** Он получает готовые метрики
и список «висящих» диалогов и пишет короткий блок «на что смотреть» — 1–2
приоритетных действия голосом РОП. Системный промпт — «Ядро роли» из
`04_sales_lead_ai_persona.md`, подавать кэшируемым префиксом
(`cache_control: ephemeral`). Задача в user-сообщении — режим «Анализ воронки» /
«Алерт», адаптированный под 3-часовой интервал. Стоимость ~$0.01–0.03 за запуск.

## 5. Расписание

Cloudflare cron работает в UTC, Алматы = UTC+5 (перевода часов в Казахстане нет).
Слоты 08:00 / 11:00 / 14:00 / 17:00 / 20:00 Алматы → cron `0 3,6,9,12,15 * * *`.
Студия работает 7 дней — оставить все дни недели. 20:00 — последний слот на сетке
«каждые 3 часа с 8:00»; ровного 21:00 на этой сетке нет.

## 6. Формат отчёта

Сообщений 5 в день в рабочий чат — поэтому КОРОТКО и по делу. Тон — РОП:
помогает, не отчитывает; не называет виноватых поимённо, говорит «в работе /
подхватите».

Промежуточный отчёт (08:00 / 11:00 / 14:00 / 17:00):
```
📊 Пульс продаж · 14:00 · 22.05

Сегодня: 9 заявок · скорость первого ответа 6 мин
За 3 часа: +4 заявки · медиана ответа 4 мин

🔴 Сейчас без ответа:
• №8874578 — ждёт 47 мин
• №8875012 — ждёт 22 мин

⚡ Действие: подхватите обе заявки сейчас — тёплые, написали сами.
```

Если за окно тихо:
```
📊 Пульс продаж · 11:00 · 22.05
Тихо: 0 новых за 3 часа, все диалоги отвечены. 9 заявок с утра.
```

Итоговый отчёт дня (20:00) — чуть полнее: всего заявок, скорость, главный вывод
дня и 1 действие на завтра. Намеренно пересекается с вечерним отчётом
продажника — объективные цифры против рассказа человека, расхождения видны.

Жёсткие правила цифр (из практики ежедневных разборов):
- считать **только живые обращения**; комментарии под постами и эмодзи-реакции
  заявками НЕ считать;
- в каждом примере диалога указывать **номер и время**;
- если данных за метрику нет — не выдумывать, честно опускать строку;
- если API отдаёт этапы воронки — добавить строку «записались на консультацию: N».

## 10. Шаги реализации

1. Изучить API message.help — что отдаёт на чтение. Выбрать ветку A/B (раздел 4).
   Авторизацию взять из `mh-bot.js` (`POST /api/app/user/login`).
2. Написать `mm-pulse-bot.js`: handlers `fetch` и `scheduled`; подсчёт метрик;
   вызов Claude API с персоной РОП; отправка в Telegram.
3. `wrangler-mm-pulse-bot.toml`: cron `0 3,6,9,12,15 * * *`, vars, KV binding.
4. `node --check worker/mm-pulse-bot.js` — проверить синтаксис.
5. `wrangler deploy`, прописать секреты.
6. Ветка B — зарегистрировать вебхук в message.help
   (`POST /api/app/projects/{id}/webhooks/`, entity `channel.message`).
7. Боевой тест — раздел 11.
8. Написать `MM_PULSE_BOT_SETUP.md`, обновить HANDOFF.md / README.md, коммит.

Telegram + cron — минимальный каркас:
```js
export default {
  async scheduled(event, env, ctx) {
    ctx.waitUntil(runDigest(env, { trigger: 'cron' }));
  },
  async fetch(request, env, ctx) {
    // ?secret=<DIGEST_SECRET> → ручной runDigest;
    // вебхук message.help → накопить событие в KV (ветка B);
    // иначе → healthcheck {"status":"ok"}
  },
};
async function sendTelegram(token, chatId, text) {
  await fetch(`https://api.telegram.org/bot${token}/sendMessage`, {
    method: 'POST', headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ chat_id: chatId, text,
      parse_mode: 'Markdown', disable_web_page_preview: true }),
  });
}
```
Время Алматы — ручной сдвиг `new Date(Date.now() + 5*3600*1000)`, не полагаться
на tz воркера. При сбое дайджеста — слать в Telegram короткое «⚠️ ошибка», чтобы
провал не прошёл незаметно (паттерн из `lead-digest.js`).

## 11. Приёмка

- `GET https://mm-pulse-bot.<account>.workers.dev/` → `{"status":"ok"}`.
- Ручной триггер `?secret=<DIGEST_SECRET>` → в рабочий чат приходит отчёт в
  формате раздела 6.
- Тестовое сообщение на WhatsApp студии → в следующем отчёте посчитано как новая
  заявка; ответ менеджера → попадает в «скорость первого ответа».
- Cron виден в Cloudflare → Worker → Triggers (`0 3,6,9,12,15 * * *`); после
  первого автозапуска приходит сообщение в чат в 08:00 / 11:00 / … Алматы.
- «Тихий» интервал → приходит короткое «Тихо: 0 новых».
- Сверить цифры с ручным «разбором за сегодня» за тот же день: расхождение по
  числу живых заявок не более ±10–15% (воронка CRM завышена автозаписями — бот
  считает по потоку сообщений, это ориентир).

## 12. Риски и ограничения

- **Зависимость от API message.help.** Если API не отдаёт нужного на чтение и не
  поддерживает второй вебхук — идём по ветке B2 (tee из `mh-bot`); тогда mh-bot
  должен быть развёрнут. Координировать с задачей деплоя mh-bot (`MH_BOT_SETUP.md`).
- **Этапы воронки CRM.** «Новый», «Прогрев» и т.п. — если API их не отдаёт, бот
  считает по потоку сообщений (новые / без ответа / скорость), без разбивки по
  этапам. Для «пульса» достаточно; этапы добавить, когда подтвердится эндпоинт.
- **Дедуп и эхо.** Исходящие сообщения бота/менеджера за «заявку» не считать;
  эхо своих сообщений отсекать по `direction` / id — как в `mh-bot.js`.
- **Спам в чате.** 5 сообщений в день — порог терпимости. Держать сообщения
  короткими; «тихий» формат — одна строка. Если команда жалуется — сузить до 3
  слотов правкой `crons`.
- **Независимость.** Пульс-бот не зависит от деплоя mh-bot — кроме ветки B2.
  Можно строить параллельно.
