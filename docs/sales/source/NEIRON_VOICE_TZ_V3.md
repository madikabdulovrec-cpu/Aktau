## Вектор A — голос НЕЙРОНа (по приоритету, go-live)

### 1. Реальный `transfer_to_human` — КРИТИЧНО для go-live

Сейчас перевод на человека — заглушка: `call_handler.py` проговаривает фразу,
ставит `state=TRANSFERRING` и всё. Реального SIP-перевода нет, extensions
захардкожены. Без этого НЕЙРОН не может принять боевой трафик — некуда
эскалировать сложный звонок.

- gateway-сторона: довести сигнализацию перевода (REFER / bridge) — PR в `main`;
- neiron-сторона: dialplan + назначение целевых extension'ов в твоей зоне;
- номера/отделы перевода — из скина (`tools_config.transfer_departments`),
  не хардкод.

→ Платформенная часть PR в `main`, dialplan — в `neiron`. ~1 сессия.

### 2. Устойчивость STT-потока

`yandex_stt.py` при обрыве gRPC-потока SpeechKit падает молча — звонок
повисает. Нужен реконнект с backoff + явный фоллбэк (фраза «связь
прервалась, перезвоните» / перевод), а не тишина.

→ PR в `main`. ~0.5 сессии.

### 3. Barge-in (перебивание голосом)

Сейчас выключен — VAD ложно срабатывает от эха TTS. Нужен sustained-speech
detector (реакция только на устойчивую речь, а не на короткий всплеск),
чтобы клиент мог перебить Алию. Заметно улучшает живость диалога.

→ PR в `main`. 1–2 сессии. Тщательно — это та зона, где легко словить регресс
(см. «STT muted during TTS», «VAD at 8kHz» в `CLAUDE.md`).

### 4. FAQ-поиск: стемминг + казахский

Сейчас FAQ-матчинг — naive keyword-overlap, без морфологии. На казахском
(падежи, агглютинация) почти не находит. Нужен стемминг/нормализация для ru
и kz, чтобы `lookup_faq` реально отвечал.

→ PR в `main`. ~0.5 сессии.

### 5. `get_doctor_schedule` / night_queue — проверка данных

Движки и миграции (`0004 doctor_schedule`, `0007 night_queue`) есть, но
tool `get_doctor_schedule` может отдавать заглушку «звоните в 9». Проверить:
применены ли миграции в проде, есть ли данные графика, отдаёт ли tool
реальные слоты. Где пусто — описать, что нужно от владельца.

→ Диагностика + при необходимости PR в `main`. ~0.5 сессии.

## Вектор B — CRM: нативные адаптеры

KomekAI **не строит свою CRM** — интегрируется с CRM, которые уже есть у
клиентов, через их нативный REST API. Архитектура готова: `gateway/crm/` —
`BaseCRMAdapter` (ABC) + фабрика `build_crm_adapter`; сейчас реализованы
`MockCRMAdapter` и `WebhookCRMAdapter` (generic-хук, односторонний пуш).
Есть ветка `feat/crm-skeleton` — сначала глянь, на чём она остановилась.

Задача — дописать конкретные адаптеры поверх `BaseCRMAdapter`. Структурных
изменений ядра не требуется, только новые классы + регистрация в `_ADAPTERS`.

### B1. Bitrix24 REST + OAuth2
- адаптер под Bitrix24 REST: найти контакт по телефону, создать/обновить
  контакт, создать сделку/лид;
- OAuth2 (refresh-token flow), токены — вне кода (env / secret);
- регистрация в `_ADAPTERS`.

### B2. AmoCRM REST + OAuth2
- то же для AmoCRM (contacts/leads), OAuth2.

Цель — **двусторонняя** синхронизация (найти → обновить → создать сделку),
не односторонний webhook. Каждый адаптер — с тестами на mock-HTTP, без
реальных сетевых вызовов.

→ PR в `main`. Приоритет — после go-live задач вектора A, либо параллельно,
если по A упёрся в действие владельца.
